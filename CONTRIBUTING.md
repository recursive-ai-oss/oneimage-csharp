# Contributing

Thanks for helping. Bug reports, reproductions, documentation fixes and
pull requests are all welcome.

## Before you start

- **Found a vulnerability?** Do not open an issue. Follow
  [SECURITY.md](SECURITY.md).
- **Found a bug?** Open an issue with the smallest image file or C# that
  shows it, the package version, the .NET version and platform, and what
  you expected. A failing test is better still. If a damaged or odd file
  triggers it, attach the file (under 1 MB) or say how to generate it.
- **Want a feature?** Open an issue first and describe the problem you
  are solving; a feature that is not discussed may not be accepted.

By taking part you agree to follow the [Code of Conduct](CODE_OF_CONDUCT.md).

## Setup

You need the .NET SDK named in `global.json`. Clone the repository and run:

```sh
dotnet build -c Release
dotnet test -c Release
```

Build output goes outside the clone: to the directory in
`ONEIMAGE_ARTIFACTS` if you set it, otherwise to a `OneImage-artifacts`
directory next to the clone (see `Directory.Build.props`). Warnings are
errors, so the build is also the analyzer check.

To run only some tests, run the built test program with a filter, for
example `$ONEIMAGE_ARTIFACTS/bin/OneImage.Tests/release/OneImage.Tests -namespace OneImage.Tests.Docs`.

The repository holds:

| Path | What it is |
|---|---|
| `src/OneImage` | the library; `Kernels/` is the only place `unsafe` code is allowed |
| `tests/OneImage.Tests` | unit, codec, kernel and documentation-sample tests |
| `tests/OneImage.AotSmoke` | a NativeAOT app that must publish without warnings |
| `tests/testdata`, `data` | small test images, crash reproductions and reference data |
| `fuzz` | fuzz targets; its [README](fuzz/README.md) says how to run them |
| `bench` | BenchmarkDotNet benchmarks and the published reports |
| `tools` | generators and scripts |

CI builds and tests on Windows, Linux and macOS, on x64 and ARM64, and
publishes the AOT smoke app.

## What a good pull request has

- **One change.** Keep a pull request to one fix or one feature.
- **A test that fails without it.** Behavior that could plausibly break
  gets a test. Kernels get a test that compares the vector path with
  its scalar reference on randomized and edge-sized inputs. Tests never
  assert on timing.
- **Documentation.** Every public member has an XML doc comment stating
  defaults, edge behavior and what fails lazily; the build fails without
  one.
- **Doc samples stay compiled.** The quick start in `README.md` and
  `src/OneImage/README.md` is the same code as `QuickStart` in
  `tests/OneImage.Tests/Docs/ReadmeSamples.cs`, which compiles and runs
  it; a test fails if a README code line is not there. The snippets in
  `docs/guide.md` and `docs/migrating.md` are mirrored in
  `DocsExamples.cs` and `MigrationExamples.cs` in the same folder. When
  you change a snippet in the docs, change it there too. The same folder
  checks that relative links in the Markdown files point at files that
  exist, and that the package readme uses only absolute links and no HTML.
- **Benchmark numbers trace to a report.** Figures in
  `docs/performance.md` and the chart come from the reports in
  `bench/results/`, never from memory; the tables and the chart are
  generated by `python3 tools/make-hero-chart.py` (see Benchmarks).
- **A changelog line** under `[Unreleased]` in
  [CHANGELOG.md](CHANGELOG.md) for anything a user can see. Mark
  breaking changes.
- **No new dependency** for the `OneImage` package: it depends on the
  .NET base class library only.
- **No `unsafe` code outside `src/OneImage/Kernels/`,** and nothing that
  parses untrusted bytes in the kernel layer.
- **Untrusted-input code is fuzzed.** A new or changed decoder or parser
  gets a fuzz target and a bounded run; a crash you fix lands in
  `tests/testdata` with a test.

## Fuzzing

`fuzz/run.sh <target> <seconds>` builds the harness, instruments it with
SharpFuzz and runs libFuzzer. The targets, the two tools it needs and how
to add a target are in [fuzz/README.md](fuzz/README.md).

## Benchmarks

Benchmarks live in `bench/OneImage.Benchmarks` and use BenchmarkDotNet
with `[MemoryDiagnoser]`. A performance change shows before and after
on the benchmarks it touches, from the same machine in the same window,
with the machine's load noted. The competitor libraries (ImageSharp
3.1.12, SkiaSharp, NetVips, Magick.NET) are referenced from the
benchmark project only.

`bench/gate.sh` runs the full comparison and writes a report like the
ones in `bench/results/`; its options are listed at the top of the
script (`--avx512`, `--tasks a,b,c`, `--repeats N`). The
x64 gate runs with AVX-512 switched off so that the AVX2 path is what
is measured. After new reports land in `bench/results/`, update the
merge in `tools/make-hero-chart.py` if the set of re-run rows changed and
run it to rewrite `docs/img/` and print the tables for
`docs/performance.md`.
